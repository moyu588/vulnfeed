# vulnfeed 二次开发与上游更新同步方案

> 制定并执行于 2026-08-27（本仓库 `dev` 分支）。
> 适用范围：本仓库的本地二开 + 持续跟进原作者上游更新。

---

## 1. 背景与三份代码的角色

| 代码位置 | 地址 | 角色 | git 远程名 |
|---|---|---|---|
| 本地仓库 | `/openclaw/github/vulnfeed` | 唯一写代码的地方 | — |
| 原作者仓库 | `https://github.com/fan-tastic-z/vulnfeed` | 新功能来源（只读） | `upstream` |
| 我的 GitHub fork | `https://github.com/moyu588/vulnfeed` | 二开成果的备份/发布 | `origin` |

数据流：

```
 fan-tastic-z/vulnfeed  (原作者 upstream)
        │  ① git fetch upstream（拉取新功能）
        ▼
 本地 /openclaw/github/vulnfeed   ← 在这里做二开
        │  ② git push origin（推送二开成果）
        ▼
 moyu588/vulnfeed  (我的 fork origin)
```

核心原理：一个 git 本地仓库可以同时挂多个远程（remote）。
“取上游更新”和“推自己成果”是两条独立通道，互不干扰。

## 2. 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 与原作者 `main` 保持完全一致 | **自己永远不往上面提交代码** |
| `dev` | 二开主分支，所有改动都在这里 | 定期把 `main` 的新功能合并进来 |
| `feat-xxx`（可选） | 某个较大的二开功能 | 从 `dev` 切出，做完合回 `dev` |

好处：`main` 上没有自己的提交，同步上游时永远是快进合并（fast-forward），
**绝无冲突**；冲突只会发生在“上游更新合并进 `dev`”这一步，范围可控。

## 3. 一次性配置（已于 2026-08-27 执行完毕 ✅）

```bash
# 1) 保存二开改动到新分支
git switch -c dev
git add -A
git commit -m "feat: 二开起步改动 (sync_data_task / scheduler)"

# 2) 整理远程：原作者改名 upstream，自己的 fork 挂为 origin
git remote rename origin upstream
git remote add origin https://github.com/moyu588/vulnfeed.git

# 3) 推送到自己的 GitHub（需认证，见 §7 待办）
git push -u origin main
git push -u origin dev
```

## 4. 日常工作流

### 场景 A：原作者出了新功能，合并进来

```bash
git fetch upstream          # ① 拉取上游新提交（只下载，不改本地代码）
git switch main             # ② main 同步上游（main 干净，永远秒合）
git merge upstream/main
git push origin main        # ③ 顺手同步自己 fork 的 main

git switch dev              # ④ 把新功能合并进二开分支
git merge main
#   —— 如有冲突，见 §5 ——
git push origin dev         # ⑤ 推送
```

### 场景 B：平时写二开代码

```bash
git switch dev
# …写代码…
git add -A && git commit -m "feat: xxx"
git push origin dev
```

## 5. 冲突（conflict）处理

当上游和你改了同一文件的同一区域时，git 会暂停合并并在文件中标记：

```
<<<<<<< HEAD
你本地写的代码
=======
上游新来的代码
>>>>>>> main
```

处理步骤：
1. `git status` 查看冲突文件（标记为 `both modified`）。
2. 打开文件人工决定保留内容，删掉 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记。
3. `git add <文件>`，全部处理完后 `git commit`。
4. 中途想放弃：`git merge --abort` 回到合并前状态，不会丢东西。

减少冲突的建议：
- 合并前先备份：`git branch dev-backup-$(date +%Y%m%d)`。
- 自己的改动尽量集中在少数文件。
- 每次合并完上游打标记：`git tag synced-$(date +%Y%m%d)`。
